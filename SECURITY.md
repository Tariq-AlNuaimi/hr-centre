# SECURITY — Fullstack Next.js Template

Template-level security baseline. **When you fork this into a project, this file is load-bearing:** every change that touches auth, roles, data classification, encryption, audit, secrets, retention, or external network calls updates this file in the same commit. The sections below describe what the template ships out of the box; downstream projects must replace placeholders, fill in data classes for the actual entities they store, and re-run the threat model on first commit.

**This template is unclassified.** It contains no real data and is not a deployment. Tier and PDPL posture are set per project — see §9.

> **This file reflects the Vercel + Neon reality** (ADR-006) as of the solo-rail optimization (ADR-007). The self-hosted machinery — Droplet, Portainer, GHCR, Caddy, MinIO, the age/rclone backup sidecar, and the deploy/rollback/restore/audit-retention workflows — was removed and no longer ships. The **data-classification rules, audit-scrubbing invariants, hard rules, and threat-model categories remain authoritative**; only the deploy plumbing changed. Forks that need operator-managed encryption keys, encrypted off-host backups, or self-hosted infra do not belong on this template — they belong on the IT team's stack from day zero.

## 1. Data classification

Every field carries one of four labels. Drives encryption, access, logging, retention. The template only ships the auth-and-audit surface; project-owned models inherit this framework.

Enforced at the query layer by `lib/pms/employee-select.ts`, which omits the column from the Prisma `select` unless the actor is entitled, so it never enters an unauthorised payload; scrubbed from `audit_logs` by `SCRUB_FIELDS`; banned as an export column by `no-restricted-export-column`; redacted in `scripts/neon-sql.mjs`. Since ADR-067 the column also holds AES-256-GCM ciphertext rather than plaintext, bound to the row's `odooId` so a ciphertext cannot be moved between employees. ADR-065, ADR-067) |

**Operational rules per class:**

- **Restricted:** never logged, never returned by an API outside the owning user's own session, never in default exports. `audit_logs.before` / `after` automatically scrub Restricted field values via `SCRUB_FIELDS` in `lib/prisma/audit-extension.ts` (see §5). Excel export is a **separate** gate (`SCRUB_FIELDS` does not touch export output): `rihal-template/no-restricted-export-column` fails `/ship` at `error` when a secret-named field is used as a `toExcel` column key, so a fork can't dump a Restricted column into a downloadable `.xlsx` (its denylist is kept a superset of `SCRUB_FIELDS` by `tests/contracts/export-column-completeness.test.ts`).
- **Confidential:** auth + role gate at the API boundary. Logged on sensitive read where the project defines one (the template doesn't ship read-side audit — write-side only).
- **Internal:** auth + role gate.
- **Public:** can appear unauthenticated.

**Downstream projects:** when introducing a new Restricted field, (1) add a row above and (2) extend `SCRUB_FIELDS` in `lib/prisma/audit-extension.ts` and `tests/contracts/audit-scrub.test.ts` in the same commit.

## 2. Authentication — current

🟢 **Auth.js v5 (next-auth beta) with Credentials provider, JWT session strategy.** Configuration lives in `lib/auth.ts`. Sign-in page: `/login` (per-locale). Middleware (`middleware.ts`) gates every non-public path and returns `401` on unauthenticated API calls. **Public paths are defined in `i18n/route-decision.ts`, which is the authority** — currently `/login`, `/forgot-password`, `/reset-password`, `/api/auth/*`, `/api/health`, `/api/internal/*` (shared-secret gated instead) and `/api/v1/*`. **The `/api/v1/*` passthrough matters:** `next.config.ts` rewrites it onto the same `/api/*` handlers, so a handler reached via `/api/v1` does NOT get the middleware 401 — which is why the wrapper, not the middleware, is the real boundary (see Boundary checks below).

- **Password hashing:** **Argon2id** (`@node-rs/argon2`, OWASP default; ADR-039) is the current algorithm — `hashPassword`/`verifyPassword` in `lib/password.ts`. The bcryptjs migration window is **CLOSED** (completed 2026-07-25, OPEN-ITEMS 12): `verifyPassword` returns `false` for any hash that is not `$argon2*`. **Operational consequence** — a user whose row still carries a pre-ADR-039 bcrypt hash cannot log in at all and must go through `/forgot-password`; there is no silent upgrade path left. `needsRehash` still re-hashes an Argon2id hash weaker than the current params on successful login. Any project-introduced reset endpoint must use `lib/password.ts`. **Never** MD5 / SHA1 / raw SHA256 / plain PBKDF2.
- **Session payload:** JWT only. Carries `{id, role}` on the `token` and exposes them on `session.user` (typed via `types/index.ts`). The `sessions` table exists because the Prisma adapter is wired (needed for OAuth account linking), but JWT sessions are not written there.
- **SSO / OAuth (ADR-024):** Microsoft Entra ID is wired into `lib/auth.ts` and is **dormant until both `AUTH_MICROSOFT_ENTRA_ID_ID` and `AUTH_MICROSOFT_ENTRA_ID_SECRET` are set** (then a "Sign in with Microsoft" button appears). `AUTH_ENFORCE_SSO=true` removes the credentials provider entirely so Entra (and its MFA) is the only way in — this closes T-02 for that deployment. New SSO users default to `VIEWER` (`mapSsoRole`, least privilege); an admin promotes them in-app. `allowDangerousEmailAccountLinking` is OFF, so an Entra email matching an existing password user is not auto-linked (anti-takeover). A Google stub remains commented for forks that want it. **Operational notes (ADR-024):** (1) Activation requires id + secret + **issuer** — issuer is mandatory so the provider can't silently fall back to the any-tenant `common` endpoint. (2) A `signIn` callback blocks **new** sign-ins by soft-deleted SSO users (the adapter path doesn't filter `deletedAt` like the credentials path does); an already-issued JWT still persists until `maxAge` — rotate `AUTH_SECRET` to revoke immediately (same accepted gap as credentials). (3) If an SSO user's email matches a **soft-deleted** credentials user, Auth.js returns `OAuthAccountNotLinked` and the SSO user is blocked until an admin **permanently** deletes the old account from the recycling bin.
- **Public paths** (no session auth required) are listed in `middleware.ts`: `/login`, `/api/auth/*`, `/api/health`, `/api/internal/*`. Internal routes are gated by a shared secret via `withInternalAuth(tokenEnv, ...)`: the `x-internal-token` header, plus -- only on routes that opt in with `{ bearer: true }` -- `Authorization: Bearer` (needed by Vercel Cron, which cannot send custom headers; ADR-018). `x-internal-token`, when present, is authoritative. Internal routes compose `withRateLimit` so secret-guessing is throttled.
- **`prismaUnfiltered` in the authorize callback** is intentional — it sees soft-deleted users so the callback can distinguish "no such email" from "deactivated user" without leaking which. The `where` clause still filters `deletedAt: null` so deleted users cannot log in.
- **`next-auth@5` is a beta release sitting directly in the auth path.** Pin the exact version and review the release notes before upgrading — a breaking change here lands on the security boundary.

**Brute-force defense:** 🟢 **Rate limiter in `lib/rate-limit.ts`, applied to POST on `/api/auth/*` at 10/min/IP.** Returns 429 with `Retry-After` when exceeded. Buckets key on `throttleKey()` (`lib/client-ip.ts`), which always partitions and never collapses distinct callers into one bucket; `/api/auth/forgot-password` additionally consumes a per-**address** bucket so a run spread over rotated IP headers still hits the account's own quota. The backend is **shared-state (Valkey + `rate-limiter-flexible`) when `VALKEY_URL`/`REDIS_URL` is set** — correct across replicas — and an in-memory token bucket otherwise (the single-container default). Horizontally-scaled deployments MUST set `VALKEY_URL` so the quota is shared (ADR-035); if Valkey is unreachable the limiter degrades to per-instance limiting (fail-safe) rather than failing open. The contract suite (`tests/contracts/rate-limit.test.ts`) asserts the bucket semantics on every push.

**Account lifecycle:** seeding creates one admin from `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD`. Downstream projects MUST rotate `SEED_ADMIN_PASSWORD` on first login or remove the seed call from the entrypoint after initial deploy.

## 3. Authorization — current

🟢 Two-role enum: `ADMIN` / `VIEWER` (`prisma/schema.prisma` `Role`). Bound to `users.role`; the JWT carries it. It held a third value, `EDITOR`, until ADR-070 retired it (see below).

> **This fork (PMS) — ADR-070, 2026-08-27.** The enum still has three values, so stored rows stay
> valid, but the platform role is **GRANTABLE only as a boolean**: `lib/validations/user.ts` exposes
> `isPlatformAdmin` and refuses a `role` key outright (`strictObject`), mapping it to `ADMIN` /
> `VIEWER` in one place. `EDITOR` gated nothing here — `withEditorAuth` is never called by any PMS
> route — and can no longer be assigned through the UI or the API; a session still carrying it is
> refused by `withAdminAuth` (pinned by `tests/contracts/api-auth.test.ts`). Note the SECOND role
> system this does not touch: §4.1's HR authority lives on `Employee.pmsRoles`, is granted only by an
> HR Super Admin, and is deliberately separate (ADR-065). Neither role system can grant the other.
>
> **The API is not the only write path — the second one is JIT SSO, and it now agrees.** On a
> federated FIRST sign-up, `mapSsoRole()` (`lib/sso/role-map.ts`) reads the IdP's groups and
> `adoptSsoRole()` (`lib/auth.ts`) persists the result, bypassing `createUserSchema` entirely
> (ADR-069) — so the boundary narrowing above did not reach it, and a group in `SSO_EDITOR_GROUPS`
> could still stamp a new account `EDITOR`. Found by the post-push breadth review of ADR-070 and
> closed on 2026-08-27: `mapSsoRole` now returns only `ADMIN | VIEWER` and no longer reads
> `SSO_EDITOR_GROUPS` at all, and the value itself was then retired from the enum
> (`prisma/migrations/20260827090000_pms_retire_editor_role`, which backfills any surviving row to
> `VIEWER` BEFORE the type swap). No effective permission changed (`EDITOR` granted nothing either way);
> what changed is that no path can write a value that looks like a privilege and is not.
> `tests/contracts/sso-role-map.test.ts` pins the refusal, so restoring the branch — or a fork
> copying the template recipe's three-value version back over it — fails a test rather than passing
> silently.
>
> `SSO_ADMIN_GROUPS` minting `ADMIN` is untouched: it is the deliberate, IT-configured feature ADR-069
> signed off. Anything unlisted defaults to `VIEWER`, and that default is the security property. A
> deployment that still sets `SSO_EDITOR_GROUPS` is not broken — the variable is simply ignored, and
> those users land on `VIEWER`, which is what `EDITOR` already meant in practice.

- **Boundary checks:** every API route handler wraps with `withAuth` (any authenticated user) or `withAdminAuth` (ADMIN only) or `withInternalAuth` (shared-secret) or `withApiAuth` (Bearer-token gate for machine/API consumers; the `/api/v1` seam) from `lib/api-helpers.ts` — **enforced by the `rihal-template/no-bare-api-route` ESLint rule at `error`**, which is what makes this a guarantee rather than a convention. Four handlers are deliberately public and allowlisted IN THAT RULE: `app/api/auth/[...nextauth]`, `app/api/auth/forgot-password`, `app/api/auth/reset-password` (these ARE the authentication surface) and `app/api/health` (liveness probe, returns only DB reachability). Adding a public route means editing the allowlist — a reviewable decision, not an omission. UI gating is defense-in-depth, **not** the boundary.
- **Role wrappers:** `withAdminAuth` (ADMIN only) is the single role gate. The template's middle tier, `withEditorAuth` (ADMIN **or** EDITOR), was REMOVED by ADR-070 along with the `EDITOR` enum value it gated on: it was never called by any route here, so it was dead authority that read as live. All four couplings went with it — `scaffold-entity --writes editor` (now rejected), `scripts/rbac-matrix.mjs`, and the two ESLint rules that named it. `no-bare-api-route` now treats a handler wrapped in it as BARE, which is the fail-closed direction and is pinned by `tests/eslint-rules/rules.test.mjs`. Finer-grained, per-resource permissions (a `can()` helper) remain a project-specific addition documented here.
- **CSRF:** state-changing routes are same-origin + cookie-based; Auth.js sets `SameSite=Lax` session cookies, which blocks cross-site form/`fetch` POSTs from carrying the session. Custom POST/PUT/DELETE routes rely on this (no separate CSRF token). If a fork adds cross-origin browser clients or relaxes `SameSite`, add explicit CSRF protection (double-submit token or origin check) and note it here.
- **Row-level scoping** (e.g. "users only see their own records") is project-specific. Add an explicit `WHERE` clause in every list / get query. Postgres RLS is not enabled by default.
- **User directory + recycling bin are ADMIN-only.** `GET /api/users`, `GET /api/users/[id]`, and `GET /api/recycling-bin` wrap with `withAdminAuth` — a non-admin cannot read the user directory (`email` / `role` / `lastLoginAt`, and since ADR-070 the linked employee's `pmsRoles`, joined so one row answers "what can this person do?"; that fact is deliberately NOT added to the visibility-scoped `GET /api/employees`) or the recycling bin (which lists soft-deleted records incl. deleted-user PII + who deleted them). The matching nav entries are hidden for non-admins (`components/layout/AppSidebar.tsx`). A fork that _wants_ a team-visible directory can relax these to `withAuth` (and unhide the nav) — note the change here.
- **`session.user.role`** is typed as `Role` via the augmentation in `types/index.ts`; callbacks in `lib/auth.ts` are cast-free.
- **OpenAPI spec + docs are auth-gated and value-free (ADR-052).** `GET /api/openapi` wraps with `withAuth` (shipped by default). The Scalar docs page (`/api-reference`) is **opt-in** — not shipped in the default template; a fork adds it with `npm run enable:api-reference` (ADR-052 2026-07-12 update). When present it does a server-side session check and `middleware.ts` gates its path (anon → login redirect); both are internal-gated (ADR-052 decision 1), so an unauthenticated caller cannot read them. The generated document describes route/schema **shapes** (field names, types) derived from the `lib/validations/` zod — it carries **no Restricted data values** and embeds no real response examples. The spec's security scheme is the existing `withApiAuth` Bearer seam; the layer adds no auth path and reads, never mutates, the zod schemas.

**Default security headers:** the static ones (X-Frame-Options: DENY — matches the CSP `frame-ancestors 'none'`, the app is never framed; X-Content-Type-Options: nosniff, Referrer-Policy, Permissions-Policy, Strict-Transport-Security) are emitted by `next.config.ts`. **Content-Security-Policy is built per-request in `middleware.ts`** (a static header can't carry a nonce). `script-src` is **nonce-based** (`'self' 'nonce-<per-request>' 'strict-dynamic'`) — `'unsafe-inline'` is removed. Middleware sets the CSP (with the nonce) on both the request and response headers; Next.js reads the nonce from the request CSP header and auto-applies it to the scripts it emits, and the inline theme script in `app/[locale]/layout.tsx` carries it explicitly. `'unsafe-eval'` is added only in dev for HMR. `style-src` still allows `'unsafe-inline'` because the UI stack (ADR-029 — Radix overlay positioning, recharts SVG/ResponsiveContainer, sonner toasts, dnd-kit drag) emits dynamic **inline `style="..."` attributes** a nonce cannot cover (a nonce-per-style migration would require every one of those libraries to route styles through a nonced `<style>` — none do). The Sentry ingest origin is added to `connect-src` when `NEXT_PUBLIC_SENTRY_DSN` is set. See finding T-05 and recipe `shared-security/3-nonce-csp`.

**Backups:** managed by Neon. The free tier has none; Neon Launch ($19/mo) adds point-in-time recovery up to 7 days. Choosing and configuring a backup tier is a per-project / IT-team decision — there is no template-managed backup pipeline anymore (removed in ADR-006).

## 5. Audit logging — current

🟢 **Schema + writer ship with the template** (`prisma/schema.prisma` `AuditLog` + `lib/prisma/audit-extension.ts`). The Prisma extension auto-records every `create` / `update` / `delete` on every model **outside the EXCLUDE set** (`AuditLog`, `Account`, `Session`, `VerificationToken`).

- **Captured per row:** `timestamp`, `entityType`, `entityId`, `action` (`CREATE` / `UPDATE` / `DELETE` / `RESTORE`), `before` (JSON snapshot pre-write, scrubbed), `after` (JSON snapshot post-write, scrubbed), `changes` (diff with `updatedAt` excluded; scrubbed fields show as `from: [redacted], to: [redacted]`), `userId` (from `AuditContext`), `ipAddress`, `userAgent`.
- **Soft-delete coverage:** `prisma.<model>.delete()` is rewritten to a soft-delete by the soft-delete extension, which is the _outermost_ hook and so bypasses the audit extension — it therefore writes its own `action: "DELETE"` audit row (with `deletedBy` set from the context). Recycling-bin **restore** and **permanent delete** go through `prismaUnfiltered` (outside the extension) and write explicit `RESTORE` / `DELETE` rows via `recordAudit()`. Password changes go through the audited client (`passwordHash` scrubbed). Net: create / update / soft-delete / restore / permanent-delete are all audited.
- **Attribution comes from `AuditContext`** seeded by `withAuth` / `withAdminAuth`, which now captures `userId`, `ipAddress` (`x-forwarded-for` / `x-real-ip`), and `userAgent`. Calls outside the wrappers (`withInternalAuth` endpoints, cron jobs, seed scripts) attribute to `null` user.
- **Bulk-write / upsert blind spot (not auto-audited):** the extension hooks only per-row `create` / `update` / `delete`. `prisma.<model>.updateMany(...)`, `createMany(...)`, and `upsert(...)` on an audited model write **no audit row** — Prisma does not decompose `upsert` into a `create`/`update` the extension can observe, so it is the same class of gap. A fork doing bulk or upsert writes must avoid them (loop per-row through the audited client) or write an explicit `recordAudit()` row alongside the op. The `rihal-template/no-unaudited-bulk-write` ESLint rule (at `error`) enforces this: it fails `/ship` on `prisma`/`prismaUnfiltered` `updateMany`/`createMany`/`deleteMany`/`upsert` against an audited model, so the blind spot can't be reintroduced silently (EXCLUDE-set models and `tests/`/`scripts/` are exempt). See ADR-010.
- **Non-atomicity (accepted limitation):** the audit row is written as a _separate_ statement after the data write, not in the same transaction (Prisma query extensions can't wrap the underlying op + the audit insert atomically without a base-client restructure that would risk the soft-delete/audit invariants). A failed audit insert after a committed write is therefore possible. For prototype scale this is accepted; a `shared`-tier project that needs guaranteed atomicity should move to DB-trigger-based audit (future ADR). See ADR-010.
- **Restricted-field scrubbing:** `SCRUB_FIELDS` in `lib/prisma/audit-extension.ts` replaces values for `passwordHash`, `password`, `refresh_token`, `access_token`, `id_token`, `session_state`, `sessionToken`, `token`, `secret`, `apiKey`, `api_key`. The contract suite (`tests/contracts/audit-scrub.test.ts`) asserts the membership and behavior.
- **Retention:** scheduled via Vercel Cron (ADR-018). `vercel.json` ships a daily cron that GETs `app/api/internal/audit-purge`, which deletes rows older than `AUDIT_RETENTION_DAYS` (default 365) in capped batches. The cron authenticates with `Authorization: Bearer $CRON_SECRET` (Vercel injects it); until `CRON_SECRET` is set the run is a silent 200 no-op (`{skipped:true}`). Manual / Actions callers POST with `x-internal-token: $AUDIT_PURGE_TOKEN`. `/deploy` provisions `CRON_SECRET` automatically; manually-connected forks must set it themselves. See finding T-06 (closed).
- **Append-only:** enforced at the application layer. No DB-level `REVOKE` is set.

## 6. Secrets

Production secrets live in **Vercel project environment variables** (set in the Vercel UI per project). They never traverse Claude chat or the operator's shell. Local development reads them from `.env` (gitignored); `.env.example` documents the shape.

| Secret                                                                  | Class                                                                                | Where               | Notes                                                                                                                                                                                                                                                                                                                                        |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AUTH_SECRET`                                                           | Restricted                                                                           | Vercel env / `.env` | JWT signing key. Rotation invalidates every session. `openssl rand -base64 32`.                                                                                                                                                                                                                                                              |

## 7. Threat model — top 5

Template-level baseline. Re-run per project on: scope expansion, new external integration, new dependency > 50 KB, host provider change, role enum change.

### T1 — Stolen credential

- **Who:** anyone with access to a user's mailbox or password manager
- **Vector:** phishing; password reuse from another breach; insider sharing
- **Blast:** full session at the user's role. ADMIN can mint users + change roles.
- **Control:** Argon2id hashes (bcrypt sunset complete 2026-07-25 — a legacy hash fails closed, reset required; ADR-039) ✅; JWT signed with `AUTH_SECRET` ✅; audit log of every write incl. the login-time rehash (passwordHash scrubbed) ✅; soft-delete-aware login ✅; **10/min/IP rate limit on `/api/auth/*`, shared-state via Valkey when configured ✅**. **No MFA** — see **T-02**.

### T2 — Audit-log snapshot leak

- **Status:** Mitigated by `SCRUB_FIELDS` in `lib/prisma/audit-extension.ts`. Contract suite asserts redaction on every push.

### T3 — Presigned upload-URL leak

- **Status:** N/A by default — the template ships no file uploads. **Only relevant if `/scale-up` adds Vercel Blob.** When it does: keep upload URLs short-lived, never log them, and never let them land in audit metadata. Revisit this entry the moment uploads are wired.

### T4 — Vercel/Neon account compromise

- **Who:** anyone who phishes or hijacks the operator's Vercel or Neon login.
- **Blast:** Vercel → can read every project env var (`AUTH_SECRET`, `DATABASE_URL`, etc.), redeploy arbitrary code, change domains. Neon → full read/write of the database, including every `passwordHash` and audit row.
- **Control:** **enable MFA on both the Vercel and the Neon account.** Rotate `AUTH_SECRET` and the Neon role credential on any suspected compromise. Use a dedicated, isolated account for project ops, not a shared personal login.
- **AI-egress sub-case (ADR-036):** when the AI layer is enabled, a Vercel-env compromise can also rewrite `AI_BASE_URL` to redirect `AI_API_KEY` + prompt content to an attacker endpoint. Rotate `AI_API_KEY` and re-pin `AI_BASE_URL` on any suspected compromise; scope the key minimally.
- **SSO-egress sub-case (ADR-045):** when Polis SSO is enabled, a Vercel-env compromise can rewrite `POLIS_ISSUER` to point OIDC discovery + the auth-code exchange at an attacker-controlled endpoint (redirecting the OAuth handshake), and can rotate `SCIM_INTERNAL_SECRET` to accept forged provisioning events. Re-pin `POLIS_ISSUER` and rotate `POLIS_CLIENT_SECRET` / `SCIM_INTERNAL_SECRET` on any suspected compromise. The soft-deleted-user sign-in block (`lib/auth.ts` `signIn` callback) still denies off-boarded accounts regardless of provider.

### T5 — Dependency / supply-chain compromise

- **Who:** a malicious or compromised npm package in the tree.
- **Blast:** arbitrary code in the build or runtime.
- **Control:** `npm audit --audit-level=high --omit=dev` and gitleaks run locally via `/ship` on every push ✅; Semgrep (`p/owasp-top-ten`, `p/secrets`, …) via `/audit` on demand ✅; pin `next-auth@5` (beta) and review release notes before bumping (§2). CI mirrors these once active at handoff.

### T-01 — No rate limit on `/api/auth/*`

**Severity:** High · **Status:** ✅ Closed (`e16a8c6`); multi-replica gap closed 2026-07-11 (ADR-035)

10/min/IP. **IP source now fails CLOSED (2026-08-17, red-team R1).** The 2026-06-05 hardening preferred `x-real-ip` over the spoofable `x-forwarded-for[0]`, but `x-real-ip` is only trustworthy when a proxy overwrites it — and Caddy's `reverse_proxy` sets the `X-Forwarded-*` family but **not** `X-Real-IP`, passing a client-supplied one straight through. On the self-host rail an attacker could therefore rotate `X-Real-IP` per request to mint a fresh rate-limit bucket every time (defeating the login and password-reset throttles) **and** write an arbitrary value into `audit_logs.ipAddress`, forging attribution. `lib/client-ip.ts` trusts **nothing** unless `RATE_LIMIT_TRUSTED_IP_HEADER` names the header the deployment's proxy guarantees. **Amended after review round 8**, because the first fix over-corrected: it keyed the rate limiter on the same strict value, so an unconfigured deployment put _every_ caller in one shared `unknown` bucket — and with the auth buckets at 10/min and 5/min, process-wide, eleven requests from any unauthenticated stranger locked every user out of signing in. `VALKEY_URL` widened that single bucket across all replicas. Header spoofing costs the spoofer their own throttle; a shared bucket costs everyone the application, so the two consumers are now split by their failure asymmetry. **Attribution** (`clientIp`) still fails closed — unset means `audit_logs.ipAddress` is absent, never forged. **Throttling** (`throttleKey`) prefers the declared header, then a platform-guaranteed one (`x-real-ip` on Vercel), then the client-supplied value prefixed `untrusted:` so it can never collide with a trusted key; only a request with no forwarding headers at all (a direct connection — local dev) shares a bucket. Rotation therefore evades one's own limit and nobody else's, and the per-**account** bucket (`subject` on `rateLimit`, wired into `forgot-password`) is the control that survives rotation. `GET /api/health` emits `warnings: ["ip-trust-unconfigured"]` while unconfigured, so the weaker throttle degrades loudly rather than silently. The bundled `Caddyfile` strips a client-supplied `X-Real-IP` and re-sets it from `{http.request.client_ip}` (resolved through a `trusted_proxies static private_ranges` chain, so it stays correct with a CDN in front instead of collapsing every user onto the LB's address) — on **both** the app and the Polis SSO ingress. **The per-instance gap remains closed:** with `VALKEY_URL` set the limiter uses shared state (Valkey + `rate-limiter-flexible`), so the quota holds across replicas instead of becoming N×configured; single-container tenants keep the in-memory bucket. Valkey-down degrades to per-instance limiting (fail-safe). Contract suite asserts both the bypass regressions and the configured behaviour.

### T-20 — Unwrapped API handler reachable unauthenticated via the `/api/v1` rewrite (High) ✅

- **Found:** 2026-07-25, whole-repo security review (`security-architect`).
- **Issue:** `next.config.ts` rewrites `/api/v1/:path*` → `/api/:path*` (ADR-013's versioning seam)
  and `i18n/route-decision.ts` passes `/api/v1` through, so the SAME handler had two reachable paths
  with DIFFERENT auth preconditions — `/api/reports` got middleware's JSON 401, `/api/v1/reports` got
  nothing. Nothing forced a wrapper: `no-bare-internal-route` only covered `app/api/internal/**`.
- **Reachability:** **Not exploitable in this tree** — all 13 routes were verified wrapped or
  intentionally public. It was a latent trap: §2 told a fork author middleware gates every non-public
  path, so the first unwrapped route a fork added would ship unauthenticated on the v1 prefix while
  the author tested `/api/...`, saw a 401, and reasonably concluded it was protected.
- **Outcome:** **Fixed.** New `rihal-template/no-bare-api-route` rule at `error` requires an auth
  wrapper on every `app/api/**/route.ts` handler, with an explicit public allowlist in the rule file
  (auth surface + health probe). Adding a public route is now a reviewable edit to a security file
  rather than an omission. 13 RuleTester cases, including that `withRateLimit` alone does NOT count
  as an auth gate. The fix does not depend on middleware, the rewrite, and route-decision.ts staying
  in sync with one another.

### T-21 — Nested Restricted values reached `audit_logs` and the admin audit UI (High) ✅

- **Found:** 2026-07-25, whole-repo security review.
- **Issue:** `scrub()` in `lib/prisma/audit-extension.ts` iterated one level deep, while its twin
  `scrubContext` in `lib/sentry.ts` already recursed over the same `SCRUB_FIELDS`. An audited write
  carrying a relation — `prisma.user.update({ where, data, include: { accounts: true } })` — wrote
  `after.accounts[0].access_token` / `refresh_token` / `id_token` **verbatim**. `computeChanges`
  compared by top-level key, so the whole relation also landed in `changes`, which
  `GET /api/audit-log` returns to admins. `audit_logs` is retained 365 days by default.
- **Reachability:** No such write exists in the shipped tree (the baseline schema has no audited
  model with an `accounts` include), so this reopened T-03 **for any fork** that adds one.
- **Outcome:** **Fixed.** `scrub` recurses through objects and arrays (Dates passed through intact);
  `computeChanges` scrubs values, not just keys. Four regression assertions added to
  `tests/contracts/audit-scrub.test.ts` — nested object, nested array, Date preservation, and a
  `computeChanges` case asserting neither the before- nor after-token appears in the serialized
  output. The absence of a nesting case is why this stayed invisible.

### T-22 — Password-reset tokens stored in plaintext (Medium) ✅

- **Found:** 2026-07-25, whole-repo security review.
- **Issue:** `forgot-password` persisted `randomBytes(32)` raw and `reset-password` matched it by
  equality, making `verification_tokens` a table of live bearer credentials. Any **read** of that
  table — a Neon branch or snapshot, a backup, a support query, a future read-only SQL surface —
  allowed completing a reset on any account with an outstanding token, no password required. That is
  the capability Argon2-hashing `passwordHash` exists to deny, reintroduced for a 1-hour window.
- **Outcome:** **Fixed.** Only `sha256(token)` is stored; the raw value goes in the email; lookup is
  by digest. SHA-256 rather than Argon2 is correct here — the input is 32 bytes of CSPRNG output, not
  a low-entropy human secret, so there is no dictionary to slow down. Same change also added the
  `deletedAt: null` filter to `reset-password`'s user lookup, which `forgot-password` already applied
  when issuing (an off-boarded account's hash could otherwise be rewritten inside the window).

### 2026-09-30 — `nodemailer` 9.0.5 → 10.0.13 (the allowlist reaches empty)

## 17. Agent-runtime hook layer (tool-time guards; Wave A2)

The gates in §14 run at **push time** (gitleaks/ESLint via `/ship`) or **review time**.
Four dependency-free Node hooks in `.claude/hooks/` (wired in `.claude/settings.json`)
guard the **agent-runtime** boundary — what Claude reads, runs, and ingests mid-session.
Blueprint: `docs/blueprints/wave-a2-security-hooks.md`; evidence:
`docs/deep-comparison/04-hooks.md` + `10-security.md`.

| Hook                      | Event                                                                | Mode                | Guards                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------- | -------------------------------------------------------------------- | ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `protect-secrets.mjs`     | PreToolUse (`Read\|Grep\|Bash\|Write\|Edit\|MultiEdit`)              | **deny**            | **Read side:** reading secret material into the transcript — `.env*` (only `.env.example` allowed), key files (`.pem`/`.key`/`.p12`/…), `~/.ssh` private keys, `.netrc`/`.pgpass`/AWS creds; printing Restricted env vars (`printenv AUTH_SECRET`, `echo $DATABASE_URL`, bare `env`). **Write side (V2-408):** a `Write`/`Edit`/`MultiEdit` payload — OR a `Bash` write (redirect `>`/`>>`, heredoc, `tee`, `sed -i`) — carrying real secret material (a high-confidence token shape: Anthropic/AWS/GitHub/Slack key, PEM private-key block; or a Restricted-var assignment with a non-placeholder, high-entropy value) into a tracked/committable file. The gitignored live store is EXEMPT — and the exemption matches `.gitignore` EXACTLY (`.env`, `.env.local`, `.env.*.local`), so `.env.production`/`.env.example`/an adversarial `x/.env.example.ts` are all still scanned. Closes the mid-session read AND write boundaries (Write/Edit/MultiEdit **and** shell writes — dropping to Bash does not bypass it) that gitleaks (commit-time) structurally can't. |
| `dangerous-commands.mjs`  | PreToolUse (`Bash`)                                                  | **deny**            | Semantic layer under the prefix-lexical permission deny-list: `rm -rf` on root/home/repo-root/system dirs (any flag order, compound commands), force pushes (flag or `+refspec`), `curl\|sh` piping, `chmod 777`, `mkfs`/`dd of=/dev/*`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `post-tool-scan.mjs`      | PostToolUse (`Read\|Grep\|Bash\|WebFetch\|WebSearch\|Task\|mcp__.*`) | **warn** (advisory) | Tool RESULTS: likely secrets (known prefixes `AKIA`/`sk-`/`ghp_`/`napi_`/…, private-key blocks, Restricted env assignments — placeholder-filtered) and prompt-injection markers in external content. Warns via context injection; never prints a matched value (pattern name + line only).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `pre-compact-refresh.mjs` | PreCompact                                                           | context re-inject   | Re-injects the binding essentials the compaction-preservation rule requires: CLAUDE.md pointer, modified/unpushed file list (git), last `/ship` status, operator goal (`docs/SESSION-HANDOFF.md`), open findings-register wave-offs.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

Design rules for this layer: the two deny hooks fail **closed** (WS-8/ADR-047 — a
security guard that can't evaluate must block, not allow; push-time gitleaks remains the
backstop, and `tests/harness/hooks.test.mjs` pins the fail-closed behavior for both);
the output-side scanner is **advisory-only** (heuristic — a false-positive block would
dead-end legitimate work; the deterministic denies live at read time and push time);
no override prefix on the deny hooks (an injected instruction could otherwise add it);
hook output **never contains a secret value** — names/paths/pattern names only.

Optional complement: `/audit` documents a **trufflehog `--only-verified`** pass
(live-credential verification on top of gitleaks; external binary, skipped with a note
when not installed).
