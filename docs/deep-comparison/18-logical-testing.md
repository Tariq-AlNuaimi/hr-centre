## 18. Logical testing

**Objective:** unit / property-based / formal / invariant / edge-case correctness testing.

**Synthesis.** The field splits three ways: _general test runners_ (Jest, Vitest — the harness that runs assertions), _property-based generators_ (Hypothesis, fast-check, proptest, rapid — auto-generate adversarial inputs and shrink failures), and _formal verification_ (Rocq/Coq, TLA+ — machine-checked proofs / model checking). What THIS template ships is neither a runner nor a generator per se: it runs `node:test` and asserts **security invariants by hand** — `tests/contracts/audit-scrub.test.ts` enumerates `SCRUB_FIELDS` and asserts each is redacted; a dozen sibling contract tests (`scrub-completeness`, `soft-delete-filter`, `export-column-completeness`, `api-auth`, `rate-limit`) pin the invariants the codebase's ESLint rules and Prisma extensions depend on — and zod validates business logic at every API boundary. That is _example-based invariant testing_, and it's genuinely differentiated (none of these ten repos ship the security invariants this repo pins). But the coverage is enumerated by a human: the audit-scrub test proves the listed fields redact, not that _no_ Restricted-shaped field escapes. That "for all inputs" gap is exactly what property-based testing closes, and fast-check (#4, same JS/TS stack, zero new runner) is the one clean, in-stack borrow. Runners are redundant (we already run tests), formal tools are massively over-weight for a prototype rail, and TDD discipline is already available via Superpowers.
