# 12. Performance optimization

**Objective:** runtime / web performance — profiling, Core Web Vitals, bundle size.

This is the template's **biggest tooling gap of the 16 categories**. Pillar #1 (Speed) is a
real review-time *gate* — `/ship`, `/code-review`, and the senior reviewer enforce RSC-first
reads, no needless round-trips, debounced inputs, and bounded payloads, and a violation blocks
green the same as a security finding. But the enforcement is **principle + human judgement
only**: the repo ships **zero automated perf tooling** — no Lighthouse run, no web-vitals RUM,
no bundle-size budget, no flamegraph profiler. So on the *measurement* objective of this
category (numbers, not norms), the field wins decisively for anything past "does the reviewer
think this looks fast." The good news is that the gap is cheap to close on this stack: Vercel
hosts the app, so Lighthouse/web-vitals/bundle-budget all bolt on via `/scale-up` without
restructuring, and a bundle budget fits `/ship`'s existing gate model exactly.

| Repo | What THEY have (concrete) | What WE have (principle-only or 'none') | Who wins for THIS objective & why (we largely lack tooling here) | Recommendation |
|------|---------------------------|------------------------------------------|-------------------------------------------------------------------|----------------|
| **GoogleChrome/lighthouse** | Automated lab audit of a URL: Performance score + Core Web Vitals (LCP/CLS/TBT), accessibility, SEO, best-practices. Runs as CLI, Node module, in Chrome DevTools, or as **Lighthouse-CI** with per-PR score assertions and budgets. | Principle-only. Pillar #1 asserts "fast" at review; no Lighthouse run, no score, no CWV number ever produced. | **THEM, clearly.** They produce an objective, reproducible performance score and CWV numbers on the actual deployed page; we produce a reviewer opinion. For the "measure web performance" objective this is exactly the missing capability. | **ADOPT (top pick).** Wire **Lighthouse-CI** against the Vercel preview URL via `/scale-up` (or enable **Vercel Speed Insights**, which is the zero-config lab+field equivalent on this host). Turns Pillar #1 from a vibe into a scored, budgeted gate. |
| **aidenybai/react-scan** | Zero-config dev overlay that highlights React components as they render and flags avoidable/slow re-renders in real time; drop-in script or npm, no code changes. | None. No render-profiling of the AntD-heavy client components; re-render waste is invisible until a human notices jank. | **THEM** for client-render diagnosis. The template's client islands (AntD tables, dnd-kit boards, recharts) are exactly where wasteful re-renders hide; we have no tool that surfaces them. | **ADOPT (dev-only, lightweight).** Add as an optional dev-mode overlay for forks with heavy client interactivity. No prod cost, no lock-in. Supersedes `why-did-you-render` (below) — pick one, pick this. |
| **aidenybai/million** | "Million.js" optimizing compiler / block-DOM that rewrites React components for faster rendering; opt-in via bundler plugin. | None — and by design. Speed here comes from RSC-first architecture (server does the work, minimal client JS), not a compiler swap. | **THEM** in raw client-render throughput, **but not for us.** On Next 16 + React 19's own compiler, Million overlaps/conflicts, and it mutates render semantics — a poor fit for a locked-stack (ADR-001), RSC-default prototype rail where most pages ship little client JS. | **NOTHING.** Conflicts with the locked stack and the RSC-first model; the architecture already avoids the problem Million solves. Would need a superseding ADR for marginal gain. |
| **QwikDev/partytown** | Runs third-party scripts (analytics, tag managers, ad/pixels) inside a web worker so they stop blocking the main thread; frees up TBT/INP. | None. | **THEM** — *if you have heavy third-party scripts.* The template ships none by default (no analytics/tag-manager baked in), so there's nothing to offload today. | **NOTHING now; revisit conditionally.** Only worth it once a fork adds heavy 3rd-party tags. Note Vercel Speed Insights / Analytics are already worker-friendly, reducing the need. |
| **webpack/webpack-bundle-analyzer** | Interactive treemap of what's in each bundle chunk — spot bloated deps and duplication visually. | None. No bundle-composition view; the "Ask before installing a dep > 50 KB" rule is enforced by human judgement, not a measured bundle diff. | **THEM** for *seeing* bundle composition. We gate dep size by policy but never visualize the actual shipped bundle, so regressions (transitive bloat, dup React, mis-imported AntD) go unseen. | **ADOPT (easy).** Use **`@next/bundle-analyzer`** (the Next wrapper around this) behind an env flag — one config line, on-demand, zero prod impact. Complements size-limit (visual vs. budget). |
| **welldone-software/why-did-you-render** | Monkey-patches React in dev to console-log components that re-rendered with equal props/state — pinpoints avoidable renders. | None. | **THEM** for the same reason as react-scan, but it's the older/heavier approach (console spam, manual per-component opt-in). | **NOTHING — choose react-scan instead.** Strictly overlaps react-scan, which is zero-config and visual. Adopting both is redundant. |
| **GoogleChrome/web-vitals** | Tiny (~2 KB) library to measure **field** LCP/INP/CLS/FCP/TTFB from real users (RUM) and report them to an endpoint/analytics. | None. No field telemetry; the app never reports how it actually performs for the stakeholders reviewing shared URLs. | **THEM** for real-user performance. We optimize for a reviewer's guess of speed but capture nothing from the actual audience the template targets (stakeholders on shared `*.vercel.app` links). | **ADOPT (via Vercel).** Don't hand-wire the lib — enable **Vercel Speed Insights**, which is web-vitals RUM productized for this exact host, surfaced as a dashboard. One dependency, `/scale-up`-able. |
| **ai/size-limit** | CI tool that computes real bundle size **and** estimated download/execution time, then **fails the build if a configured budget is exceeded**. Framework presets incl. Next.js. | None. Bundle size is never measured or budgeted in `/ship`; there is no automated size regression gate. | **THEM.** This is the single field tool whose *shape* matches the template best: a hard pass/fail CI budget — exactly how `/ship` already gates security and unbounded queries. We have the gate philosophy but no perf budget in it. | **ADOPT (best gate-fit).** Add `size-limit` with a Next preset as a `/ship` step (or CI job), budgeting the client bundle. Turns "Ask before a >50 KB dep" from policy into an enforced number. |
| **jlfwong/speedscope** | Fast in-browser flamegraph viewer for CPU profiles from many sources (Node `--prof`, Chrome, py-spy, etc.) — read/interactive profile exploration. | None. No profiling capture and no flamegraph viewing anywhere in the toolchain. | **THEM** for deep profiling, **but low relevance to us.** It's a *viewer* — it needs a captured profile, which the template never produces; serverless Vercel functions make ad-hoc Node profiling awkward anyway. | **NOTHING (keep in back pocket).** Only useful once you're already capturing profiles for a specific hot path; no standing wiring warranted for a prototype rail. |
| **clinicjs/node-clinic** | Node.js server-side diagnostics suite — Doctor (event-loop/CPU/mem), Flame (flamegraph), Bubbleprof (async), HeapProfiler — for finding backend bottlenecks. | None. No server-side profiling of API routes / Prisma paths. | **THEM** for Node backend profiling, **but poor fit for the deploy model.** Clinic profiles a long-running Node process you drive with load; the template runs as ephemeral Vercel serverless functions, so its workflow doesn't map cleanly. The N+1 / unbounded-query concerns it would catch are already gated at review by Pillar #4. | **NOTHING for the default rail.** Relevant only if a fork self-hosts the Docker rail (ADR-023) as a long-running server under real load; even then, DB-level tooling (postgres-mcp, pghero from category #1) is usually the better first move. |

**Top thing to adopt:** Enable **Vercel Speed Insights** (lab + field Core Web Vitals, zero-config on this host) and add **`ai/size-limit`** as a `/ship` bundle budget — together they convert Pillar #1 from a review-time opinion into a measured, gate-blocking number.
