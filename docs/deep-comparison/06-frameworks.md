# Deep comparison — Category 06

## 06. Config / workflow frameworks

**Objective:** full Claude Code workflow/command frameworks & starter templates — the tit-for-tat, one row per repo vs. THIS template.

_This template is a vertical, single-stack factory: Next.js 16 + Prisma 7 + Auth.js v5 + Ant Design 6, wired to one deploy target (Vercel + Neon). Its harness is a gated lifecycle — `/blueprint → /quickstart → /ship → /qa → /handoff` — with 25 skills, 26+ ADRs, 10 enforced ESLint security rules, 5 enforcement hooks, and the Five-Pillars gates baked into `/ship`. ADR-022 evaluated and REJECTED ruvnet/claude-flow wholesale (unverified perf claims, destructive preinstall, off-Anthropic egress, `--dangerously-skip-permissions`)._

**Synthesis.** The field splits into three shapes: stack-agnostic *methodology layers* (superpowers, spec-kit, BMAD, SuperClaude) that inject a workflow but ship no running product; *marketplaces/installers* (wshobson, davila7, awesome-claude-code) that distribute portable components; and *task/review point-tools* (claude-task-master, OneRedOak, claude-flow). This template is the only entry that is an **end-to-end product factory** — it ships a running schema, auth, audit log, and a provision-to-live-URL pipeline, and *enforces* its workflow at a `/ship` gate rather than merely suggesting it. So it wins decisively for its own objective (idea → shared URL on one governed stack) but loses on portability and on depth in three specific sub-areas — spec-artifact rigor (spec-kit), task-graph decomposition (task-master), and the sheer breadth of ready components (wshobson/davila7) — which are exactly where it should borrow rather than rebuild.
