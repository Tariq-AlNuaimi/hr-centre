# 16. Testing

**This template's testing posture (the baseline every row compares against):** `/ship`
(`npm run ship`) runs `npm test` — the **contract suite** (`tests/contracts/*.test.ts`,
run on Node's built-in `node --test` runner via `tsx`) plus the ESLint-rule tests
(`tests/eslint-rules/*.test.mjs`) — and **hard-fails on red before any push**. There are
also **component tests** (`tests/components/*.test.tsx`) on `@testing-library/react` +
`global-jsdom`, **integration tests** (`tests/integration/`), and **Playwright** flows under
`tests/uat/` driven by `/uat` and `/manual-uat`. The philosophy is _invariant-first_: the
14 contract files assert security/data invariants (audit-scrub completeness, soft-delete
filtering, rate-limit, api-auth, export-column completeness, design-tokens) rather than
chase line coverage. Test **volume is deliberately modest** — contract + component + a
handful of E2E, not an exhaustive unit suite. No coverage gate (`test:coverage` exists but
is not enforced), no AI test-generation, no property-based testing.

## Synthesis

For raw testing capability the field is far deeper than this template: these are the actual
frameworks and engines (Playwright, Vitest, Jest, pytest, Selenium, Testing Library) that
the template _consumes_ — it drives Playwright and uses Testing Library + a Vitest-shaped
runner, so on those rows the honest verdict is "they are the tool, we are a thin user of it."
Where the template genuinely leads is **enforcement and invariant-targeting**: a red test
blocks the push, and the tests that exist assert the exact security invariants (audit scrub,
soft-delete, export leakage) that a generic coverage number would miss. The template's two
real gaps versus the field are **AI test-generation / coverage-closing** (keploy, qodo-cover)
and **breadth of automated coverage** — it has the gate but a small suite behind it.
