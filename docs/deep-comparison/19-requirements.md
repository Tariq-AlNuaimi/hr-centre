## 19. Requirements gathering

**Objective:** specs / PRDs / user stories / SDD / brainstorming — pinning down *what* to build (and why) before code.

**Synthesis.** This template already runs a real requirements gate: `/blueprint` produces user stories + happy/worst scenarios + an architecture sketch + tier + open-questions-resolved-via-`AskUserQuestion`, committed to `docs/blueprints/`, and CLAUDE.md defers to Superpowers brainstorming for real multi-file features while requiring a market-scan section — so the discipline these ten repos exist to bootstrap is wired into the build loop, tiered (lightweight confirm for disposable `/quickstart`, full committed doc for real work) and structurally enforced (`/ship` phase A blocks a new route/migration surface that ships without a blueprint). Where the field genuinely leads is in three orthogonal places our prose-blueprint doesn't do today: **ID-based traceability** (spec-kit's FR-###/SC-###/US# threading spec→tasks→QA), **EARS-notation acceptance criteria** (the Kiro-lineage repos' constrained "WHEN…THE SYSTEM SHALL…" phrasing that makes each requirement individually testable), and a **delta / change-proposal model for edits to existing surface** (OpenSpec) — the last being a live gap because `/ship`'s blueprint gate only fires on *added* routes/migrations, so a behavior change to an existing route escapes it. Everything else in the field (agent-persona role-play, persistent standards layers, heavyweight phase gates) is over-weight for a single-operator prototype rail whose value is speed-to-URL.
