# 07. Scalability

**Objective:** build/verify systems that handle growth.

**Synthesis.** For this objective the field splits cleanly into two things the template does *not* do: **load/scale infrastructure** (k6, Locust, Vitess, Citus — real horizontal-scale and load-generation systems we have no equivalent of) and **runtime DB diagnostics** (PGHero, postgres-mcp, pghero-style N+1/slow-query surfacing that inspect a *live* database under load). What THIS template actually ships is a *static, pre-merge gate*: `/ship`'s `scanScalability` reads the ~250-char argument block after every `.findMany(` call and hard-fails any call missing a `take`/`skip`/`cursor`/`parsePagination`/`paginat` bound (scripts/ship.mjs:41-68), and Pillar #4 blocks unbounded queries, N+1, and N×1 bulk paths at code-review time. That gate is genuinely differentiated — none of these ten repos stop unscalable code from *merging* — but it verifies scalability by *reading code*, never by *running load*. So several repos here win outright on the "verify under growth" half of the objective, and the honest recommendation is to borrow one load-tester and one live-DB advisor via `/scale-up` rather than pretend the static scan covers them.

| Repo | What THEY have (concrete) | What WE have (the /ship scan or 'none') | Who wins for THIS objective & why | Recommendation |
|------|---------------------------|------------------------------------------|------------------------------------|----------------|
| **grafana/k6** | Production-grade load-testing tool; JS-scripted VUs, ramping stages, thresholds, checks, distributed/cloud runs, CI-native. Generates *real* traffic against a URL to measure p95/throughput/error-rate under growth. | `scanScalability` — static bound-token check on `.findMany(` args; no traffic generation at all. | **k6 wins.** It empirically *verifies* a deployed system handles growth; our scan only proves individual queries are paginated in source. Different, complementary halves — but the objective says "verify systems that handle growth" and only k6 exercises the running system. | **Adopt via `/scale-up`.** Wire k6 as an opt-in load-test rig against the `*.vercel.app` URL (smoke: ramp to N VUs, threshold on p95). Highest-value borrow in the category. |
| **QAInsights/k6-mcp-server** | Tiny MCP server exposing `execute_k6_test` / `execute_k6_test_with_options` (duration, VUs) so an agent can drive k6 from Claude and stream results back. Python 3.12 + uv + local k6 binary. | none — no way to run a load test from a session. | **k6-mcp-server wins** for the *agentic* slice: it lets Claude itself launch and read a load test, which is exactly this template's operator-iterates-with-Claude model. | **Adopt as the delivery mechanism for the k6 borrow.** If/when k6 is wired via `/scale-up`, register this MCP so `/uat` or a new `/load-test` can invoke it. Thin wrapper, low risk. |
| **locustio/locust** | Distributed Python load testing; user-behavior classes, web UI, master/worker fan-out to millions of RPS, community MCP exists. Same job as k6, Python-native. | none. | **Locust wins** on the same axis as k6. | **Nothing (pick one).** k6 is the closer fit (JS matches the stack, single binary, MCP already exists). Adopting both is redundant; note Locust only if a Python shop prefers it. |
| **vitessio/vitess** | MySQL horizontal sharding / connection pooling / query routing at YouTube scale; a database clustering *system*. | none — and the stack is locked to **Postgres/Prisma** (ADR-001), not MySQL. | **Vitess wins** on raw scale-out capability, but it's off-stack (MySQL) and enormous. | **Nothing.** Wrong DB engine and a scale tier this prototype rail will never hit; adopting it would violate the locked stack. Neon read-replicas / Postgres scale-up is the in-stack path if reads ever saturate. |
| **citusdata/citus** | Postgres extension turning Postgres into a distributed, sharded, columnar-capable cluster (scale-out reads/writes, parallel queries). Actually on-stack (Postgres). | none — single Neon Postgres, no sharding. | **Citus wins** on Postgres scale-out; it's the in-engine answer to "handle growth" if a single Neon instance is ever exhausted. | **Nothing now, note for the growth path.** Prototype rail doesn't need sharding; if a fork genuinely outgrows Neon, Citus (or Neon's own scaling) belongs in a future `/scale-up` recipe. Premature today. |
| **ankane/pghero** | Postgres performance dashboard: surfaces slow queries (pg_stat_statements), missing/unused/duplicate indexes, table bloat, connection counts, live queries. Reads a *running* DB. | `scanScalability` catches unbounded `.findMany` in source, but sees nothing about live query plans, index usage, or N+1 as it actually executes. | **PGHero wins** for *diagnosing* a live DB under load — the empirical complement to our static scan. Our gate prevents one class (unbounded list reads); PGHero finds the rest at runtime. | **Adopt-lite via `/scale-up`.** Optional Neon-connected PGHero (or equivalent) for slow-query/missing-index surfacing once a fork has real traffic. Lower priority than k6 since prototypes rarely have load. |
| **crystaldba/postgres-mcp** | Postgres MCP Pro: EXPLAIN plan analysis, **index tuning** (Anytime DTA algorithm over thousands of candidate indexes, `hypopg` hypothetical indexes), database-health checks (buffer cache, vacuum, bloat, unused/duplicate indexes, connection health), safe read-only SQL — all callable by an agent. | none — no EXPLAIN, no index advice, no live health check; static bound-token scan only. | **postgres-mcp wins** decisively for agent-driven DB *tuning*: it's PGHero's diagnostics **plus** index recommendation, exposed as MCP so Claude uses it directly. Best on-stack, agent-native fit in the category. | **Top adopt (DB side).** Register via `/scale-up` against the Neon URL in read-only mode; lets a session run EXPLAIN and get index advice on real slow queries — the runtime layer our static gate can't provide. |
| **wshobson/agents** | ~37k-star agent marketplace incl. `performance-engineer`, `database-optimizer`, `deployment-engineer` — prompt-defined subagents that reason about bottlenecks, indexing, caching, load-test design. | none — our scan is a mechanical regex gate, not a reasoning agent; `senior-code-reviewer` is quality/security-focused, not perf-specialized. | **Mixed.** Their agents give broader *advisory* perf reasoning we lack; our gate gives a hard *block* they lack. For "verify handles growth," their agents plan the load test / index change our tooling would then run. | **Borrow the prompt, not the repo.** Lift a `performance-engineer`-style checklist into `/code-review` or a `/scale-up` note (index/N+1/caching prompts). No install needed — it's a markdown persona. |
| **VoltAgent/awesome-claude-code-subagents** | 100+ curated subagent definitions incl. `postgres-pro`, `sql-pro`, `database-optimizer` — SQL/Postgres tuning personas. | none (same as above). | **Their catalog wins** as a *source of personas*; our repo wins on enforcement. Overlaps heavily with wshobson. | **Nothing beyond cherry-picking.** If we lift a perf persona, take the single best `postgres-pro`/`database-optimizer` prompt; don't vendor the list. |
| **VoltAgent/awesome-agent-skills** | Large cross-harness curated skills index; may include scaling/perf skills but is a *link directory*, not runnable tooling. | none — but the template already has its own curated lifecycle skills. | **Neither for verification** — it's a discovery hub, not a tool. For actually verifying scale, k6/postgres-mcp win; for finding *more* skills, the list helps marginally. | **Nothing.** Discovery aid only; nothing here that k6 + postgres-mcp + a lifted perf persona don't already cover. |

**Top thing to adopt:** wire **k6 (via QAInsights/k6-mcp-server)** for agent-driven load testing and **crystaldba/postgres-mcp** for live EXPLAIN/index tuning through `/scale-up` — together they add the *runtime* scalability verification our static `scanScalability` gate structurally cannot do.
