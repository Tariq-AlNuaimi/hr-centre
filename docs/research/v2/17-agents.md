# 17 — Agents (role-agent model vs enterprise multi-agent patterns)

> **Scope note.** Section-A task #2. This benchmarks our **dev-harness role-agent model** (`.claude/agents/*.md` + built-in Plan/Explore/general-purpose) against the 2026 enterprise multi-agent ecosystem: orchestration frameworks, agent registries/governance, agent evals + guardrails, and model-tier/cost routing. Methodology per `docs/research/v2/METHODOLOGY.md`: 4-lens top-10 → head-to-head → Recommendation (KEEP / KEEP+HARDEN / ADOPT / REPLACE / ADD-AS-OPTION / DEFER + Fit 1–5 + ADR impact) → category verdict table. Builds on `15-architects-ai-era.md` (Part C role-agent tweaks) and **cross-refs `07-ai-agent-stack.md`** without contradicting it.
>
> **The load-bearing distinction (read first).** There are TWO agent runtimes in this repo and they must not be conflated:
>
> 1. **The dev-harness runtime** — Claude Code subagents / the Claude Agent SDK that runs `scout`, `senior-code-reviewer`, etc. **at development time** in the operator's session. THIS file governs it.
> 2. **The application AI runtime** — the framework a _fork's shipped product_ uses to run agents at request time. `07-ai-agent-stack.md` already decided that: **BUILD a thin wrapper on Anthropic's native Tool Runner**, Managed Agents for hosted/scheduled, defer LangGraph/Mastra/CrewAI. THIS file does **not** re-open that call. When LangGraph/CrewAI/AutoGen appear below, they are benchmarked as _harness-orchestration patterns to learn from_, not as candidates to replace our application runtime.
>
> Lens tags: `BT` battle-tested · `HS` highest-star/popular · `ENT` enterprise-grade · `OSS` best permissive/self-hostable. Star counts point-in-time (as-of **2026-07**).
>
> **Current-events catches up front (these move defaults):**
>
> - **Microsoft AutoGen → maintenance mode.** AutoGen (~58.7k★) + Semantic Kernel were merged into the unified **Microsoft Agent Framework**, GA v1.0 **April 2026**; AutoGen itself is now maintenance-only (the community fork is **AG2**). Don't cite AutoGen as a live default. [6][7]
> - **Promptfoo acquired by OpenAI** (Mar 9 2026) — core stays MIT/model-agnostic, but the eval-tool now has an OpenAI owner. [carried from 07]
> - **Langfuse acquired by ClickHouse** (Jan 2026) — MIT + self-host intact. [11]
> - **Claude Agent SDK billing split** — as of **June 15 2026** the Agent SDK draws from a **separate monthly credit**, not the interactive subscription pool; matters for a harness that fans out many subagents. [3]
> - **AWS Agent Registry (Bedrock AgentCore) — Preview Apr 9 2026**; the first mainstream _governed agent catalog_ (MCP + A2A native). Signals that "agent sprawl governance" is now a named enterprise category (OutSystems 2026: **96%** of enterprises run agents in prod, only **12%** can govern them). [13][14]

## 1. Role-agent decomposition model

**One line:** How we split work across named specialist agents. **Current:** 4 custom (`scout` haiku, `senior-code-reviewer` sonnet, `security-architect` opus, `sre` sonnet) + 3 built-in (Plan, Explore, general-purpose); a proposed `ai-eval` (ADR-036/042). This is an **orchestrator-worker + specialist-review** topology, not a candidate to buy — we benchmark the _pattern_.

| #   | Pattern / Reference                                                                                | Lens tag(s) | Provenance (as-of 2026-07)                                                                    | Maturity                               | Why it ranks                                                                                                                       |
| --- | -------------------------------------------------------------------------------------------------- | ----------- | --------------------------------------------------------------------------------------------- | -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **Orchestrator-worker (lead planner + scoped sub-agents)** — Anthropic multi-agent research system | BT ENT      | Anthropic Engineering, 2025; "multi-agent beats single by up to ~90% on breadth tasks" [3][2] | Proven in prod (Claude Code, Research) | The canonical shape; our main session = lead, `scout`/reviewers = workers. Directly maps to what we have.                          |
| 2   | **Reviewer/critic agent (LLM-as-judge on a peer's output)**                                        | BT          | Anthropic; Husain/Shankar evals canon [carried from 15]                                       | Mature                                 | `senior-code-reviewer` + `/code-review` are exactly this for CODE. Gap: nothing reviews _model outputs_.                           |
| 3   | **Plan-and-execute (separate planner, then executors)**                                            | BT HS       | LangGraph/CrewAI/OpenAI-Agents core loop [1][5][8]                                            | Mature                                 | Our built-in **Plan** agent + `EnterPlanMode` is a lightweight version; enterprise fw's formalize it as a graph.                   |
| 4   | **Specialist swarm / handoffs (peer agents pass control)**                                         | HS          | OpenAI Agents SDK handoffs; CrewAI crews [5][8]                                               | GA                                     | We use _fixed roles_, not dynamic handoff. Fine for a gated pipeline; swarm adds nondeterminism we don't want.                     |
| 5   | **Supervisor / hierarchical teams**                                                                | ENT         | LangGraph supervisor, MS Agent Framework GroupChat [1][7]                                     | GA                                     | Overkill for a solo-operator harness; relevant only if `/qa` fans out to many parallel reviewers.                                  |
| 6   | **Read-only recon agent (cheap tier, throwaway context)**                                          | OSS BT      | Our `scout` (haiku); Anthropic "sub-agent for fact-finding = 1 agent" sizing [2]              | Shipped                                | Best-in-class cost pattern; most enterprise fw's lack a _deliberately cheap_ recon tier. We lead here.                             |
| 7   | **Guardrail/policy agent (pre/post-execution gate)**                                               | ENT         | NeMo/Guardrails-AI as agents; MS "governance as the gate" [7][12]                             | Emerging                               | We enforce policy via _hooks + ESLint_, not an agent — arguably better (deterministic), but no agent owns adversarial output-side. |
| 8   | **Eval/judge agent (scores outputs vs rubric)**                                                    | HS          | Braintrust/Langfuse judge loops [11]                                                          | GA                                     | Our **proposed `ai-eval`** — the #1 missing role.                                                                                  |
| 9   | **SRE/ops agent (operational readiness)**                                                          | ENT         | Our `sre`; DORA-2025 platform-quality [carried from 15]                                       | Shipped                                | We already have this — ahead of most harnesses, which stop at code review.                                                         |
| 10  | **Security-architect / threat-model agent (design lens)**                                          | ENT         | Our `security-architect` (opus); STRIDE canon                                                 | Shipped                                | We have it; distinctively runs on the _opus_ tier by design (ADR-022). Rare in OSS harnesses.                                      |

**Head-to-head:** Our decomposition is a **fixed-role orchestrator-worker pipeline with four review lenses** (correctness, security-design, operational, and — proposed — AI-output), which is the right shape for a _gated, deterministic_ harness: unlike CrewAI/OpenAI-Agents swarms that let peers hand off control dynamically (great for open-ended tasks, bad for a repeatable ship-gate), our roles are stable and each maps to a named gate. The three built-ins (Plan/Explore/general-purpose) cover planning + broad search without us maintaining code. Against the best enterprise pattern (Anthropic's orchestrator-worker with fan-out sizing 1/2–4/10+), our one true gap is **fan-out is undocumented** — `/qa` doesn't formalize when to spin 1 vs. 4 parallel reviewers — and **no output-side reviewer** (`ai-eval`). We are notably _ahead_ on the cheap-recon tier (`scout`) and on shipping ops + security-design agents that most OSS harnesses lack.

**Recommendation: KEEP+HARDEN (Fit 5/5).** The role split is correct and well-lensed. Harden by: (a) **ship `ai-eval`** to close the output-side reviewer gap (the one structurally missing lens); (b) add a **fan-out sizing heuristic** to `/qa` (1 agent = fact-find, 2–4 = compare/parallel-review, 10+ = research — Anthropic sizing [2]); (c) document the topology explicitly as "orchestrator-worker + fixed-lens review" in `docs/agent-memory.md` so it isn't rediscovered. Do **not** add dynamic handoff/swarm — it fights the gated-pipeline design. **ADR impact:** extends ADR-036/042 (ai-eval); minor note in the ADR-022 routing doc.

**One line:** How agents are defined, discovered, and versioned. **Current:** flat `.claude/agents/*.md` with YAML frontmatter (name/description/tools/model), discovered by the harness; **no versioning, no registry, no ownership metadata, no changelog.**

**Head-to-head:** The 2026 signal is unambiguous — **agent governance became a named category** (AWS Registry preview, MS Entra Agent ID, the OutSystems 96%/12% gap [14]) — but every mainstream registry is a _runtime_ catalog for fleets of deployed application agents, massive over-buy for **7 git-tracked markdown files** in one repo. The right-sized steal is the **agent-card/manifest** idea from A2A + Backstage (#4/#5): add owner, semantic version, capability summary, and a changelog line to each agent's frontmatter, versioned in git — governance without infrastructure. This mirrors exactly how `15-architects-ai-era.md` recommended a "software catalog manifest" for the handoff.

**Recommendation: KEEP+HARDEN (Fit 4/5).** Keep flat markdown; **add lightweight registry semantics in-place**: (a) extend agent frontmatter with `version:`, `owner:`, and a one-line `capabilities:` summary; (b) maintain a generated `docs/AGENT-REGISTRY.md` index (name/model/tools/version/owner) — the harness analog of `REPO-MAP.md`, cheap to auto-refresh at SessionStart; (c) bump agent versions via the existing `@changesets` flow. Defer any real registry (AWS/MS) — it's an _application-fleet_ tool, revisit only if a fork ships many runtime agents. **ADR impact:** small ADR "agent-definition versioning + registry index" (net-new, P2).

## 4. Agent evals + guardrails

**One line:** Do our agents get evaluated, and are their outputs guardrailed? **Current:** **No.** Our agents are prompt-engineered and confidence-filtered (`senior-code-reviewer` reports ≥80 only) but there is **no eval suite for agent quality and no runtime guardrail** on model outputs. The proposed `ai-eval` gate (ADR-036/042) is the first eval concept — but it targets a _fork's AI endpoints_, not our harness agents.

| #   | Candidate                                           | Lens tag(s) | Stars (2026-07) | License                             | Role                      | Why it ranks                                                                                                          |
| --- | --------------------------------------------------- | ----------- | --------------- | ----------------------------------- | ------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 1   | **Langfuse**                                        | HS OSS BT   | large           | MIT (**ClickHouse-owned Jan 2026**) | Eval + trace              | Best self-host: LLM-as-judge, custom scorers, human feedback, prompt registry. Free, no per-seat. [11]                |
| 2   | **Braintrust**                                      | ENT HS      | —               | Commercial (generous free tier)     | Eval CI/CD                | Strongest **eval-gated deployment** workflow; LLM-as-judge + scorer primitives; 10k evals free. [11]                  |
| 3   | **Promptfoo**                                       | OSS HS      | large           | MIT (**OpenAI-owned Mar 2026**)     | Eval + redteam            | CLI-first, CI-gate-native, model-agnostic; also does prompt-injection red-teaming. Best fit for a `/ship`-style gate. |
| 4   | **Arize Phoenix**                                   | OSS BT      | large           | **Elastic License 2.0**             | Trace + eval              | OTel-native (OpenInference); pairs with the OTel/SigNoz seam (WS-4). License = not pure-permissive.                   |
| 5   | **NeMo Guardrails (NVIDIA)**                        | ENT OSS     | ~6.5k           | Apache-2.0                          | Runtime rails             | 5 rail types (input/dialog/retrieval/execution/output) + Colang DSL. Heaviest, most capable. [12]                     |
| 6   | **Guardrails AI**                                   | OSS         | ~6.6k           | Apache-2.0                          | Output validation         | Python validator hub you compose; structured-output + schema enforcement.                                             |
| 7   | **LLM-Guard (Protect AI)**                          | OSS ENT     | mid             | MIT                                 | Prompt/response sanitizer | Middleware scanner chain (PII, injection, toxicity); simplest drop-in guardrail.                                      |
| 8   | **Anthropic prompt-injection / output classifiers** | ENT         | (API)           | Anthropic                           | Runtime guard             | Native, Claude-first; the on-thesis guard for a Claude-first fork's AI endpoints.                                     |

**Head-to-head:** Two distinct needs hide here. **(a) Harness-agent evals** — do `scout`/`senior-code-reviewer` actually produce good reviews? — for which the cheapest credible instrument is a **golden-set of past diffs with known findings**, run through Promptfoo or a lightweight `node:test` harness in CI; full platforms (Langfuse/Braintrust) are over-buy for 4 agents. **(b) A fork's shipped-AI-endpoint evals + guardrails** — where the `ai-eval` gate (ADR-036/042) is the eval half and a **guardrail layer is entirely missing**. Among guardrails, NeMo is the most capable but heavy (Colang), Guardrails-AI/LLM-Guard are lighter, and for a **Claude-first** shop the native Anthropic classifiers + the Tool Runner's per-turn approval hook are the on-thesis default. Promptfoo is the standout for _our_ purposes because it is CLI/CI-gate-native and model-agnostic — but note it is now **OpenAI-owned** (Mar 2026), a governance flag even though the core stays MIT.

**Recommendation: ADOPT (net-new), staged (Fit 4/5).**

- **Harness agents:** ADD a small **agent-eval golden-set** (past diffs → expected findings) run via Promptfoo or a `node:test` judge in CI — makes `senior-code-reviewer`/`ai-eval` quality measurable, not vibes. Low effort, high leverage. (P1)
- **Fork AI endpoints:** **ship the `ai-eval` gate** (already scoped, ADR-036/042) AND **add a guardrail seam** — a `lib/ai/guardrails.ts` behind the provider adapter using the native Anthropic classifiers + Tool Runner approval hook as the default, with NeMo/LLM-Guard as documented `/scale-up` upgrades. The eval gate without a guardrail leaves the _runtime_ injection/PII surface open. (P0 for eval, P1 for guardrail seam)
- **Tooling default:** **Promptfoo** for CI eval gating (model-agnostic, self-hostable) + **Langfuse** (MIT, self-host) for trace/eval storage if a fork needs observability — both honor Docker-first self-host. Flag the OpenAI/ClickHouse ownership changes in the ADR.
- **ADR impact:** extends ADR-036/042 (ai-eval), new ADR "agent-eval golden-set + AI-guardrail seam."

## 5. Model-tier routing & cost governance

**One line:** How work is routed to the cheapest capable model, and how cost is metered. **Current:** ADR-022 tier table (haiku/sonnet/opus) — **advisory prose**, enforced only via subagent `model:` frontmatter + the operator's `/model` choice; **no auto-router, no runtime routing, no per-request cost metering** (deliberately: "a metric with no token accounting is theater").

| #   | Candidate                                                    | Lens tag(s) | Provenance (as-of 2026-07)      | License/Model         | Why it ranks                                                                                                              |
| --- | ------------------------------------------------------------ | ----------- | ------------------------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 1   | **ADR-022 static tier routing (ours)**                       | OSS         | subagent frontmatter + `/model` | Anthropic/Claude Code | Deterministic, zero-infra, right for a harness; `scout`=haiku, reviewers=sonnet, security=opus.                           |
| 2   | **RouteLLM (lm-sys)**                                        | OSS HS      | framework, peer-reviewed        | Apache-2.0            | The routing _brain_: ~85% cost cut at ~95% GPT-4 quality on MT-Bench. Benchmark-specific — re-prove on real traffic. [16] |
| 3   | **NotDiamond**                                               | HS ENT      | powers OpenRouter Auto          | Commercial            | Learns per-query best model from YOUR eval data; predicts model identity. The "learned router." [16]                      |
| 4   | **OpenRouter Auto Router**                                   | HS ENT      | hosted aggregator               | Commercial            | `cost_quality_tradeoff` dial 0–10; one key, hundreds of models, outage-aware fallback. The hosted "buy." [16]             |
| 5   | **LiteLLM / Portkey (gateway routers)**                      | BT OSS/ENT  | AI gateways                     | MIT / commercial      | Route + cost-track + key-govern at the proxy; the enterprise cost-metering seam for a fork's runtime calls.               |
| 6   | **Cascade routing (cheap-first, escalate on quality check)** | BT          | RouteLLM/production guides [16] | pattern               | The pattern to steal for a fork's runtime: try haiku, escalate to sonnet/opus on a confidence check.                      |

**Head-to-head:** Again two layers. **(a) Harness routing** — ADR-022's static tier map is _correct and deliberately un-automated_: with only 3 tiers and a handful of agents, a learned router (RouteLLM/NotDiamond) would add infra + a metric the doc itself calls "theater" without real token accounting. The honest hardening is not a router but **enforcement**: a soft `/ship` or session-receipt check that recon/bulk work actually ran on haiku and that opus escalations are logged — cost discipline as an _observed_ fact, not a promise. **(b) A fork's runtime routing** — enterprise forks shipping AI endpoints _do_ need cascade routing + per-deploy cost metering (RouteLLM-style 40–85% savings, plus per-tenant/per-deploy attribution for deploy-per-tenant billing), which belongs behind the `lib/ai` provider adapter, not in the harness. LiteLLM/Portkey are the gateway option if multi-provider governance is ever required (kept in back-pocket per C07/C10).

**Recommendation: KEEP (harness) + ADD-AS-OPTION (fork runtime) (Fit 5/5).**

- **Harness:** KEEP ADR-022 static routing. Optional harden: a **lightweight routing-adherence check** (session receipt aggregation: did cheap work run cheap? are opus escalations logged?) — turns advisory into _observed_, no auto-router. (P2)
- **Fork runtime:** ADD-AS-OPTION a **cascade-router + cost-meter recipe** (`/scale-up` + `lib/ai/router.ts` behind the provider adapter) — cheap-model-first with a quality-check escalation, per-deploy token metering. RouteLLM/NotDiamond as the routing brain, LiteLLM as the gateway if multi-provider. (P1)
- **ADR impact:** amend ADR-022 (add the adherence-check note, keep advisory stance); new `/scale-up` recipe + a small ADR for the runtime router seam.
