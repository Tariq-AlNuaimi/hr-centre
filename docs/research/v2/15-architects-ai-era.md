# C15 — Enterprise-tool architects (AI era) → concrete harness tweaks

> **Shape note.** This item is not a 4-lens tool comparison like C01–C14 — it benchmarks _ideas and people_, then converts them into concrete changes to OUR two products: (1) the Next.js+Prisma+Auth.js app template, and (2) the Claude "AI-development OS" in `.claude/` (skills/hooks/agents/gates). Citation discipline follows `METHODOLOGY.md`: inline `[n]`, numbered `Sources` at the end, dated where a fact is time-varying. Ground truth for our harness is `docs/harness-inventory.md` + `docs/repo-architecture.md`; the pivot (enterprise-only, deploy-per-tenant, Docker-first, Claude-first) is honored throughout.

**The one-sentence thesis.** Our harness already _is_ a small internal developer platform whose "paved road" is a set of gates — so the canon that matters most is **software-governance-as-code (fitness functions)** wrapped in a **platform-as-a-product** delivery model, and the AI era adds exactly one new axis the harness doesn't yet gate: **the quality of model _outputs_ and the specs/evals that drive them.** The highest-leverage move is to mirror the `senior-code-reviewer` pattern for AI outputs and lift the gate-trio into an OPA-style policy layer.

## Part B — AI-era engineering patterns (2025-26), mapped to our harness

Legend: **HAVE-IT** (a real gate/agent exists) · **THIN** (advisory or partial) · **MISSING** (net-new).

| Pattern                                | What it is (2025-26)                                                                                                                                                                                                                                 | Cite     | Our harness status                                                                                                                                                                                                                                                                 |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Spec-driven development (SDD)**      | The answer to "vibe-coding drift": a spec (requirements→design→tasks) is the durable artifact the agent implements against. Kiro (EARS notation), GitHub Spec Kit (93k★, 30+ agents), Tessl; Fowler's team documents the pattern.                    | [15]     | **HAVE-IT (thin).** `/blueprint` (ADR-033) + the PreToolUse blueprint-gate are exactly SDD — but the gate checks a file _exists_ with a matching `Scope:` glob, not that the spec is _good_ or in a rigorous notation. Steal EARS-style acceptance criteria + tasks decomposition. |
| **Eval-driven development (EDD)**      | "If you can't write the eval, you can't ship the AI feature." Deterministic/code-based evals for hard-fails, LLM-as-judge for subjective; run as **CI gates** (favor cheap deterministic checks in CI, reserve judge for offline). Husain & Shankar. | [16]     | **MISSING.** No eval concept anywhere. The single biggest AI-era gap: the moment a fork ships an AI endpoint (C07), there is no gate on output quality. This is the payoff of Part C.                                                                                              |
| **Agent-in-the-loop / reviewer-agent** | A second agent reviews the first's output before it's trusted (LLM-as-judge on code + on model outputs).                                                                                                                                             | [12][16] | **HAVE-IT (for code).** `senior-code-reviewer` (post-push) + `/code-review` (pre-push diff) are exactly this **for code**. **MISSING for model outputs** — no reviewer judges what a fork's AI endpoint emits. Mirror the pattern.                                                 |
| **Sub-agent orchestration**            | Divide a task across scoped sub-agents with isolated context; size the fan-out to the task (1 / 2–4 / 10+). Anthropic's multi-agent research system.                                                                                                 | [12]     | **HAVE-IT (thin).** `scout` (haiku recon) + `senior-code-reviewer` + built-in Explore/Plan. No formal fan-out sizing in `/qa`; no memory-directory sub-agents. Steal the sizing heuristic + `memory:` frontmatter.                                                                 |
| **Context engineering**                | "What configuration of context is most likely to produce the desired behavior?" — context is a finite resource; prune/compact/offload to keep the window focused.                                                                                    | [12]     | **HAVE-IT.** Token-policy (ADR-019), `context-watchdog`, `pre-compact-refresh`, `scout` offloading, `agent-memory.md`. | **Evals-as-CI-gates**                  | Eval suites gate merges the way tests do; deterministic checks in the hot CI path, judge offline.                                                                                                                                                    | [16]     | **MISSING.** `/ship` has 14 code gates, 0 eval gates. | **LLM-as-judge for review**            | A model scores outputs against a rubric where deterministic assertion is impossible (subjective quality, tone, safety).                                                                                                                              | [16]     | **HAVE-IT (implicit).** `/design-qa`/`/uat` already use Claude as a judge of UI. **Not formalized** as a reusable judge with a versioned rubric. | **Model-tier routing for cost**        | Route each request to the cheapest capable model; RouteLLM (ICLR 2025) hit 95% GPT-4 quality on ~14% strong-model calls (~75-85% cost cut). Enterprise forks need a **runtime router** (cascade + per-tenant cost metering).                     |
| **Harness / scaffold thinking**        | The durable asset isn't the code, it's the _scaffold that produces code_: Skills (progressive disclosure), sub-agents, hooks. Anthropic's Agent Skills.                                                                                              | [13][14] | **HAVE-IT (this repo's whole thesis).** 26 skills, 13 hooks, gate-trio. The mature core. Extend to _scaffold the scaffold_: `/scaffold-agent`, `/scaffold-ai-endpoint`.                                                                                                            |
| **"Design the factory, not the part"** | Willison's _dark factory_: 70-95% of code is agent-written; the human role shifts to **designing + monitoring the system that writes software**; spec quality = code quality; "ambiguous requirements become silent bugs."                           | [17]     | **HAVE-IT (culturally), THIN (enforced).** The repo's stated purpose. **The synthesis of Part B:** our harness is strong on _context/memory/orchestration/scaffold_ (the AI-_process_ patterns) and strong on _code_ review/gates — but has a **hole exactly where the AI era adds risk: the model's own outputs.** Spec-driven ✓(thin), reviewer-agent ✓(code only), eval-driven ✗, evals-as-CI ✗, runtime cost routing ✗. Part C closes that hole using the harness's own proven pattern (gate + committed adjudication artifact + a mirrored reviewer agent).

### C.5 The 6th pillar question

**Recommendation: add a 6th "AI-Quality / Eval" pillar — but only for forks that ship AI, and enforce it via the AI-eval gate, not prose.**

- **Why a distinct pillar, not fold-in:** the existing High-Quality pillar governs _deterministic_ correctness/UX/a11y (things `/ship` + axe + tests can assert). AI output quality is **non-deterministic and needs a fundamentally different instrument** — eval suites + LLM-as-judge with a versioned rubric [16]. Folding it into High-Quality would let a fork claim the pillar green with zero evals, exactly the "checkpoint theater" the inventory warns about. A named pillar makes the gap _visible and adjudicated_.
- **Definition (draft):** _AI-Quality — every AI-driven output path has a deterministic eval suite (hard-gated in CI) and, where subjective, an LLM-as-judge rubric; hallucination/injection/cost/latency are bounded and monitored; prompts+model IDs are versioned config (16-factor [20])._
- **Scope guard so it doesn't tax non-AI forks:** the pillar is **inert until an AI endpoint exists** (same conditional as the AI-eval gate) — mirroring how Arabic/RTL and Docker stay inert until opted into. A fork with no AI endpoint auto-passes.
- **Where:** add to `docs/uat-rubric.md` (the pillars doc) + wire into `/ship`/`/qa` alongside the AI-eval gate; record as ADR-035.

## The highest-leverage sequence (if you do only five things)

1. **`ai-eval` agent + AI-eval `/ship` gate + `evals/` convention (P0)** — closes the one AI-era hole by mirroring the harness's own most-trusted pattern (`senior-code-reviewer` + gate + adjudication artifact). Fitness-function thinking [3] applied to model outputs [16].
2. **`/scaffold-ai-endpoint` (P0)** — makes the secure+evaluable AI path the _default_ path (Netflix paved road [5]), and guarantees the eval gate has something to run.
3. **6th "AI-Quality" pillar, conditional-on-AI, enforced by the gate not prose (P0)** — makes AI output quality a _visible, adjudicated_ gate instead of folding it invisibly into High-Quality.
4. **Unify deny-hooks + lint + ship gates into one fail-closed, whole-diff policy pass (OPA-style) (P1)** — fixes the inventory's #1 systemic gap (everything fails open; added-files-only blindness) using the canonical policy-as-code model [18].
5. **`security-architect` + `sre` agents + Docker-first `/deploy` + SBOM/container-scan-as-fitness-functions (P1)** — operationalizes the raised enterprise floor and the Docker-first / deploy-per-tenant pivot (DORA "quality internal platform" [8] + Humanitec orchestrator [10]).
