# Enterprise Architects & AI-Era Patterns — Benchmark for the "Enterprise Factory" Pivot

> Research section for repositioning the template from a prototype rail into an **enterprise app + agent factory**. Generated 2026-07-10 via web scan (real orgs, engineering blogs, star counts) + grounding in `docs/enterprise-pivot-analysis.md`, `docs/harness-inventory.md`, and `CLAUDE.md`. Analytical, but ends in concrete, actionable harness tweaks (Part C).

## Summary

The industry has already built the thing this repo is pivoting toward, twice over. **Part A** (how enterprise orgs run an "app factory") converges on a stable pattern: a _catalog/portal_ (Backstage, Port) that exposes _golden-path scaffolds_ (software templates, Nx/Turborepo generators, Plop/Yeoman/Cookiecutter), all fenced by _policy-as-code_ (OPA/Conftest) and _architecture fitness functions_ (Building Evolutionary Architectures) that run as CI gates. Our harness is a **single-repo, single-operator instance of exactly this stack** — `/scaffold-entity` is a software template, the ESLint rules + `/ship` gates are policy-as-code, and the pillar gates are fitness functions — but it lacks a _catalog_ (multi-app inventory) and its policies are TypeScript-hardcoded rather than an externalized policy layer. **Part B** (AI-era patterns) shows the second convergence: spec-driven development (GitHub Spec Kit, ~90–120k stars in ~10 months), eval-driven development, LLM-as-judge in CI, sub-agent orchestration, context engineering, and model-tier routing — every one of which the harness _already partially implements_ (blueprint = spec, senior-code-reviewer = LLM-as-judge, scout/senior = sub-agents, agent-memory = context engineering, ADR-022 = tier routing). The gaps are precise: **no eval loop for the coming AI product surface, no reviewer for model outputs, no security-architect role, and tier-routing tuned for cost-thrift rather than an enterprise security floor.** Part C turns those gaps into a prioritized change list: an `ai-eval` judge agent, a `threat-model` security-architect agent, an AI-eval + container-scan + SBOM gate trio extending the existing ADR-032/033/034 pattern, docker-first lifecycle skills, and a 6th "AI-quality" pillar.

## Part A — How enterprise engineering orgs structure an "app factory"

### The discipline: platform engineering + golden paths

The organizing idea is **platform engineering** (Team Topologies' "platform team" enabling "stream-aligned teams") delivering **golden paths** — Spotify's term for a supported, opinionated, paved route to production; Netflix's equivalent is the **"paved road"** [1][2]. The point is not to _forbid_ deviation but to make the supported path the path of least resistance: self-service, standardized, and secure by default. Red Hat frames a golden path as "a supported, opinionated path that codifies best practices so a developer can go from zero to a running service without reinventing security, CI, and observability each time" [2].

This is _precisely our template's thesis_ — the fork-and-ship unit that ships to standard automatically — but expressed at org scale rather than repo scale. The pivot's job is to raise our single-repo golden path to the enterprise floor those orgs enforce.

### The four building blocks

**1. IDP / service catalog.** **Backstage** (open-sourced by Spotify, now a CNCF incubating project) is the de-facto standard — ~36k GitHub stars, 45k+ contributors, 13,500+ orgs, and by one estimate ~89% market share of the developer-portal space [3]. Its **Software Templates** feature is the golden-path mechanism: a scaffolder engine reads a manifest (input variables + actions) and publishes a new, standards-compliant service to GitHub/Azure DevOps [1][3]. Commercial alternatives trade build-effort for time-to-value: **Port** ships a production portal "in a week vs. months for Backstage" and is recommended below ~50 devs; **Humanitec** is an _orchestrator_ (developers declare intent in a Score file; platform engineers control how intent maps to real cloud resources); **Cortex/OpsLevel** focus on service maturity scorecards [4][5]. The category lesson: portals give _visibility_, orchestrators _provision_, and picking the wrong category is costlier than the wrong tool within a category [5].

**2. Scaffolding / generators.** Below the portal sits the actual code-emitting layer. **Nx generators** are TypeScript functions with AST-level modification, project-graph awareness, and a migration/codemod system (~28k stars) [6]. **Turborepo**'s `turbo gen` is a thin wrapper over **Plop.js** (Handlebars templates + simple file ops) [6]. Language-agnostic standalones: **Yeoman** (programmatic generation, can even generate tests for the generated code), **Cookiecutter** (template library, Python-native), **Hygen** (fast, embedded) [6]. The enterprise pattern is generators-as-guardrails: _every new package is born conforming_, which is exactly what `/scaffold-entity` does for a CRUD entity.

**3. Policy-as-code.** Guardrails that run in CI and _block the merge_. **Open Policy Agent (OPA)** is the most broadly deployed cloud-native policy engine (~10–12k stars) [7][8]; **Conftest** (OPA's config-file front-end, Rego policies over HCL/JSON/YAML) is the standard for gating IaC and configs in git [8][9]. The reference architecture is _layered_: "Checkov in CI, Spacelift gating the apply, Gatekeeper at admission, SCPs as last-line — each layer catches what the layer below can't see" [9]. The maturity insight that maps directly onto our harness: **"when important system properties can be expressed as executable checks, governance moves to the point where change happens"** [10].

**4. Architecture fitness functions.** From _Building Evolutionary Architectures_ (Ford/Parsons/Kua) — automated checks that preserve architectural characteristics as a system evolves. The 2nd edition explicitly connects fitness functions with automating architectural governance, and cites OPA/policy-as-code as the enforcement precedent [10]. Thoughtworks now discusses "architecture-as-code" as the next enterprise-governance frontier [10]. Our five pillars _are_ fitness functions; `/ship`'s unbounded-query scan and complexity budget are textbook examples.

Both are cheap to add and both are what "enterprise" auditors actually ask to see. We should **not** bolt on Backstage — it's a >50-dev, dedicated-platform-team investment [5] — but we should produce the two artifacts a Backstage would generate (a catalog and Rego policies), because they are the paper trail enterprise governance demands.

## Part B — AI-era engineering patterns (how building changes when agents write the code)

The second industry convergence: a set of patterns for building _with_ and _for_ agents. Each is mapped to our harness as **HAVE / THIN / MISSING**.

| Pattern                                         | What it is (cited)                                                                                                                                                                                                                                                                                                     | Our harness today                                                                                                                                                                                                                     | Status                                                                                                                                                                                            |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Spec-driven development (SDD)**               | Spec is the source of truth, written first, kept, treated as canonical; the code is "the last mile." GitHub **Spec Kit** (Specify→Plan→Tasks→Implement), AWS **Kiro** (Requirements→Design→Tasks), **Tessl**. Spec Kit hit ~90–120k ★ in ~10 months and supports 29 agent integrations incl. Claude Code [11][12][13]. | `/blueprint` (ADR-033) is a spec gate: user stories + happy/worst scenarios + a `Scope:` glob, enforced by a PreToolUse deny hook. This is genuinely SDD — arguably _ahead_ of Spec Kit because ours is _enforced_, not just tooling. | **HAVE** (strong). Thin spot: blueprint checks a file _exists_, not that the spec is _good_ (harness-inventory §11). Spec Kit's Plan/Tasks decomposition is richer than our single blueprint doc. |
| **Eval-driven development**                     | Write evals _before/alongside_ the feature; the eval suite is the regression net for non-deterministic code. "When agents write the code, the spec is where intent lives; when agents _are_ the product, the eval is where correctness lives" [11][14].                                                                | Nothing. `/ship` tests deterministic code; there is **no eval harness** for model outputs because there is no AI product surface yet (Axis 2).                                                                                        | **MISSING** — the single biggest AI-era gap for the pivot.                                                                                                                                        |
| **LLM-as-judge / agent-as-judge**               | An LLM scores another LLM's output on a rubric; used in CI to gate PRs, post per-scorer regression comments; 2026 best practice = _classifier cascade_ (cheap judge first, frontier judge only on disagreement), _locked judge model versions_, code-evals for deterministic + LLM-judge for subjective [14][15].      | `senior-code-reviewer` **is** an LLM-as-judge over _code diffs_ (5 lenses, ≥80-confidence filter). The pattern is in-house and load-bearing.                                                                                          | **HAVE** for code; **MISSING** for model/agent outputs. The exact same pattern needs a second instance pointed at AI-endpoint outputs.                                                            |
| **Evals as CI gates**                           | Eval score → pass/fail gate on every PR; "cheap, fast, statistically significant — pick two or it's theater"; Level-3 maturity = multi-metric eval with regression detection in CI; Level-5 = eval scores gate runtime tool access [14].                                                                               | `/ship`'s 18 gates are CI-gates-as-fitness-functions for code. No eval gate.                                                                                                                                                          | **THIN→MISSING**: the _gate machinery_ exists (`/ship`, PreToolUse hooks, the ADR-032/033/034 pattern); no eval _content_ plugs into it yet.                                                      |
| **Sub-agent orchestration**                     | Orchestrator-workers: a central LLM decomposes and delegates to specialized workers; routing by task type; Anthropic's "start simple, add agentic complexity only when simpler underperforms" [16][17].                                                                                                                | `scout` (haiku, read-only investigator) + `senior-code-reviewer` (sonnet, breadth reviewer) + built-in Explore/Plan/general-purpose. Main session is the orchestrator.                                                                | **HAVE** (mature for a template). Thin: only 2 custom role-agents; no ai-eval, no security-architect, no SRE/deploy agent.                                                                        |
| **Context engineering**                         | Curate what enters the context window; durable memory across sessions; handoff artifacts; Anthropic's "Effective context engineering for AI agents" [16][17].                                                                                                                                                          | `agent-memory.md` (durable, ~150-line budget, SessionStart-surfaced), `SESSION-HANDOFF.md`, `/handoff-session`, `pre-compact-refresh` hook, `docs/REPO-MAP.md`. This is a _deliberate, multi-layer_ context-engineering system.       | **HAVE** (a genuine strength). Thin: 150-line memory budget has no overflow warning (harness-inventory §9).                                                                                       |
| **Memory / handoff (cross-session durability)** | Long-horizon agents need state that survives container churn; "pushed-or-it-didn't-happen."                                                                                                                                                                                                                            | The Stop hook hard-blocks on unpushed commits; `/handoff-session`; branch-scoped in-flight state vs. `main`-reaching durable knowledge.                                                                                               | **HAVE** (unusually rigorous).                                                                                                                                                                    |
| **Model-tier routing for cost**                 | Route easy/common → Haiku, hard/unusual → Sonnet/Opus; the routing workflow pattern [16][17].                                                                                                                                                                                                                          | ADR-022 tier table (haiku scouts / sonnet build+review / opus architecture).                                                                                                                                                          | **HAVE**, but tuned for **cost-thrift**, not an enterprise _security_ floor — needs re-tuning (Part C).                                                                                           |
| **Harness / scaffold thinking**                 | The "harness" (loop + tools + context mgmt + sub-agents) is the product, not just the model; Anthropic released the Claude Agent SDK to expose the Claude Code harness; Managed Agents pair a tuned harness with production infra [16][17].                                                                            | The _entire_ `.claude/` + `scripts/` + `docs/` layer **is** a harness — this is the repo's second product. The pivot explicitly names it "an AI-development operating system."                                                        | **HAVE** (this is the repo's identity). Thin: the harness governs _code_ well; it has zero primitives for governing a _shipped AI runtime_ (`lib/ai/*` doesn't exist yet).                        |
| **Guardrails / safety for AI output**           | Input/output guardrails, injection defense, PII egress checks on model I/O; parallelization pattern for guardrails [16].                                                                                                                                                                                               | `post-tool-scan` + `protect-secrets` hooks guard the _dev-time_ transcript. Nothing guards a _product_ model endpoint's input/output.                                                                                                 | **MISSING** for the product surface.                                                                                                                                                              |

**Prose takeaway.** The striking finding is that our harness has _independently reinvented_ most AI-era patterns and, for two of them (enforced spec-driven development via `/blueprint`, and LLM-as-judge via `senior-code-reviewer`), is arguably _ahead_ of the named OSS tools because ours are **enforced gates**, not opt-in tooling. The pivot's AI product surface (Axis 2) creates one clean new frontier: everything the harness does for _code_ (spec, judge, gate, guardrail) must be **duplicated for model outputs**. That symmetry is the design principle for Part C.

**Prose takeaway (the payoff).** The pivot does not require inventing a new governance model — it requires **cloning the existing one onto the AI surface**. The harness already proves that a gate + a committed adjudication artifact converts advisory behavior into enforced behavior (ADR-032/033/034). Do the same four things for model outputs that we already do for code: **spec it** (`/blueprint` → already covers AI features via `Scope:`), **judge it** (`ai-eval` agent mirroring `senior-code-reviewer`), **gate it** (AI-eval gate mirroring blueprint-gate), and **guardrail it** (Secure-pillar AI I/O checks mirroring `protect-secrets`). Simultaneously, harden the _existing_ harness for the raised floor: fail-closed hooks, full-diff gate scope, opus on security, container/SBOM scans. That is the entire Part-C program, and every item is a variation on something the repo already does well.
